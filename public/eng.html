Project Specification Document: SecurityScorecard Findings Dashboard - Cyber Security project

1. Introduction

This project is an interactive dashboard displaying security findings retrieved using the SecurityScorecard API. The goal is to provide users with a centralized view of security findings from various companies in their portfolio, allowing filtering, display by Severity levels, and detailed viewing of each finding. The project is built with a Client-Server architecture using both client-side (Frontend) and server-side (Backend) technologies.

2. Project Goals

  • Provide a visual and intuitive interface for viewing security findings from the SecurityScorecard API.
  • Categorize and display findings by severity levels (High, Medium, Low).
  • Display statistical data and charts representing the distribution of findings by severity levels and factors.
  • Enable filtering of displayed findings based on various criteria (Company, Factor, Grade, Date Range).
  • Provide the ability to "Drill-down" to view full details of each finding.
  • Ability to export the displayed data (all findings or filtered findings) to a CSV file.
  • Basic access protection for the dashboard using a simple login screen (Client-side authentication).
  • Use the SecurityScorecard API to fetch data in real-time (or as provided by the API).

3. Technologies Used

The project integrates several technologies on both the client and server sides:

  • HTML5: Basic structure and organization of page content (login.html, index.html).
  • CSS3: Visual design and styling (including the use of Bootstrap and custom CSS).
  • JavaScript:
    • Client-side (Frontend): Handling user interactions, fetching data from the Backend API, processing and displaying data in tables and charts, local data filtering, handling the Modal (popup window) for finding details, basic login logic, and exporting data to CSV.
    • Server-side (Backend - Node.js): Creating a Web server, managing routing, exposing an API Endpoint, fetching data from the SecurityScorecard API using HTTP Requests, initial processing of the data, and returning it to the client in JSON format.
  • API (SecurityScorecard): The external data source. The project integrates with it to retrieve security findings.
  • Express: Server-side Framework in Node.js. Used to create the Web server, define Routes, and handle HTTP Requests/Responses.
  • Axios: Client library for making HTTP Requests from the server-side (in app.js) to the SecurityScorecard API.
  • Dotenv: Library for loading environment variables from a .env file (used to store the SecurityScorecard API Key).
  • Bootstrap 5: Popular CSS Framework that allows for building responsive and styled user interfaces quickly (Grid system, Components like Cards, Tables, Navs, Modals, Dropdowns, buttons, forms).
  • Font Awesome: Library for icons (Font-based icons) used to improve the visual appearance (buttons, titles).
  • Chart.js: JavaScript library for creating custom charts (used to create the Bar and Doughnut charts in the dashboard).
  • jQuery: JavaScript library used in the project mainly for interaction with Bootstrap's Modal (It would have been possible to use Bootstrap 5 JS alone, but jQuery was included in the code).
  • MongoDB / Mongoose: Important note: These libraries appear in package.json and package-lock.json (project dependencies), but they are not actively used in the provided server code (app.js). They were likely included for future development or experiments, but the current dashboard does not connect to this NoSQL database and does not store data in it.

4. Architecture

The project is implemented using a Client-Server architecture:

  1. Client (Browser): Based on HTML, CSS, JavaScript files. Displays the user interface, handles the login logic (Client-side), makes HTTP GET calls to the Backend API, processes the received data, displays it in tables and charts, and handles filtering and export.
  2. Server (Node.js + Express): Based on the app.js file. Serves as an HTTP server that delivers the static Frontend files. Additionally, exposes an API Endpoint (/api/findings) which acts as a Proxy between the Client and the SecurityScorecard API. The Server handles authentication with the SecurityScorecard API (using the API Key), fetches the relevant information, and passes it to the client in standard JSON format. It does not permanently store the data in a database.
  3. External API (SecurityScorecard): External service that provides security findings via a REST API.

5. Functional Requirements

  • User Login:
    • Display login screen (login.html).
    • Receive username and password.
    • Client-side check for matching login details against predefined values ('admin', 'securityscorecard').
    • Store login state in sessionStorage.
    • Redirect to the dashboard page (index.html) in case of successful login.
    • Display an error message in case of incorrect details.
    • Redirect to the login page if the user attempts to access the dashboard without login state in sessionStorage.
  • Main Dashboard:
    • Display project title and author details.
    • Display action buttons: Refresh, Export, Logout.
    • Display statistical summary of findings: Total, High, Medium, Low.
    • Display a Bar Chart detailing findings by factors and severity level.
    • Display a Doughnut Chart detailing finding distribution by severity level.
  • Filtering Findings:
    • Display filter controls: Company selection, Factor selection, Grade selection, Date range selection (Today, This Week, This Month, All Time).
    • Dynamic update of tables according to filter selections.
  • Detailed Findings Display:
    • Division of findings into Tabs by severity level: High, Medium, Low.
    • In each tab, display a table with main columns for each finding: Company, Finding (Title), Factor, Factor Grade, Score Impact, Number of Issues, Date/Time.
    • Provide a "Details" ("Drilldown") button in each table row.
  • Finding Details (Modal):
    • Display a popup window (Modal) on clicking the "Details" button.
    • Display extended details about the selected finding, including Company, Domain, Title, Description, Severity Level, Factor, Factor Grade, Score Impact, Number of Issues, Date/Time, Issue Type, and all full data in JSON format.
  • Data Export:
    • "Export" button with a dropdown menu.
    • Export options: All findings, Filtered findings (according to active filters), Findings by specific severity level (High, Medium, Low).
    • Export the data to a file in CSV format.
  • Data Refresh:
    • "Refresh Data" button that performs a repeated call to the Backend API and updates the entire interface.
  • Loading State:
    • Display a loading screen (Loading Overlay) while data is being fetched from the Backend API.

6.1.2 JavaScript Logic (Client-side Script in index.html)

  • Loading Data (loadData): Asynchronous function that performs a Fetch to the API Endpoint on the Backend (/api/findings). Displays and hides the loading screen. Updates the global variable allFindings. After loading, calls functions to update statistics, tables, charts, and filters.

Code Example - Fetch API call: 


async function loadData() {
    showLoading(true);
    try {
        const response = await fetch('/api/findings');
        if (!response.ok) {
            throw new Error('Failed to fetch findings');
        }
        allFindings = await response.json();
        updateCounts();
        populateTables(); // Populate initial tables
        updateCharts();
        populateFilters(); // Populates filters and sets up listeners
        setupExportButtons(); // Setup export buttons
        showLoading(false);
    } catch (error) {
        console.error('Error loading findings:', error);
        alert('Failed to load findings. Please try again.');
        showLoading(false);
    }
}
  • Updating Statistics (updateCounts): Counts the number of findings for each severity level (High, Medium, Low) and overall from the allFindings variable and updates the corresponding HTML elements (#highCount, #mediumCount, #lowCount, #totalFindings).
  • Updating Charts (updateCharts): Collects the relevant data (number of findings by factor and risk, number of findings by risk) from the allFindings variable. Updates the Chart.js objects (factorChart, severityChart) and causes them to re-render.

Code Example - Chart.js Update:

  • Populating Filters (populateFilters): Collects the list of unique companies and factors from all findings in the allFindings variable. Adds them as options (<option>) to the corresponding dropdown lists (#companyFilter, #factorFilter). Calls the setupFilterListeners function to set up change listeners.
  • Setting Up Filter Listeners (setupFilterListeners): Adds an Event Listener (type 'change') to each of the filter controls. Each change in one of them triggers the applyFilters function.
  • Applying Filters (applyFilters): Called every time one of the filters changes. Reads the current values from all filter controls. Iterates through the findings for each severity level in the allFindings variable, applies the filterFinding function to them, and creates new arrays of filtered findings. Empties the HTML tables and repopulates them only with the filtered findings using the addFindingToTable function.
  • Filtering Function (filterFinding): A local Client-side function that receives a finding object and the current filter values. Returns true if the finding meets all filter conditions, and false otherwise. Includes logic for filtering by company, factor, grade, and dates (Today, Last Week, Last Month).

Code Example - Date Filtering Logic: 


if (date) {
    if (!finding.created_at) return false; // Skip if no date

    const findingDate = new Date(finding.created_at);
    const now = new Date();

    if (date === 'today') {
        const todayStart = new Date(now.getFullYear(), now.getMonth(), now.getDate());
        const todayEnd = new Date(now.getFullYear(), now.getMonth(), now.getDate() + 1);
        if (findingDate < todayStart || findingDate >= todayEnd) return false;
    } else if (date === 'week') {
        const sevenDaysAgo = new Date(now);
        sevenDaysAgo.setDate(now.getDate() - 7);
        if (findingDate < sevenDaysAgo || findingDate > now) return false;
    } else if (date === 'month') {
        const thirtyDaysAgo = new Date(now);
        thirtyDaysAgo.setDate(now.getDate() - 30);
        if (findingDate < thirtyDaysAgo || findingDate > now) return false;
    }
}
return true; // Finding passes all filters
  • Populating Table (populateTables, addFindingToTable): populateTables is called after data loading (or applying filters) and clears all table bodies. addFindingToTable receives a finding and adds a new row to the specific table (High/Medium/Low). Creates the HTML for the row including a "Details" button with data-* attributes to store the severity level and the original index of the finding in the allFindings array (important for Drilldown). Adds an Event Listener to the "Details" button.

  • Fetching Data from SecurityScorecard API (axios):
    • The function at /api/findings uses axios to make calls to the SecurityScorecard API.
    • First step: Fetching the list of portfolios (/portfolios).
    • Second step: Loop through each found portfolio, and fetch the list of companies within each portfolio (/portfolios/:id/companies). Collecting all found companies (while removing duplicates).
    • Third step: Loop through each unique company, and fetch the list of factors for this company (/companies/:domain/factors).

    • Handling factors with low grades (D, F) without details in issue_summary - create a general finding for them.

7. Data Flow

  1. Login:
    • User accesses the base URL (/).
    • Express server redirects them to /login.html.
    • The browser loads login.html and accompanying CSS/JS files (Bootstrap, Font Awesome).
    • User enters details and submits the form.
    • JavaScript code in login.html checks the details. If valid, stores in sessionStorage and redirects to /index.html.
  2. Initial Dashboard Load:
    • The browser accesses /index.html.
    • The JS code at the beginning of index.html checks sessionStorage. If authenticated, proceeds. If not, redirects to /login.html.
    • The browser loads index.html and accompanying CSS/JS files (Bootstrap, Font Awesome, Chart.js, jQuery, Custom CSS).
    • An Event Listener on DOMContentLoaded triggers loadData().
    • loadData() displays a loading screen and performs a Fetch to /api/findings.
    • Server (app.js): The /api/findings path is activated. The server loads the API Key from .env. Performs a series of asynchronous API calls to the SecurityScorecard API (Portfolios -> Companies * for each company -> Factors/Findings). Processes and categorizes the data. Builds a JSON object with high, medium, low arrays. Returns the JSON to the client.
    • Client (Browser): Receives the JSON object. Stores it in allFindings. loadData() hides the loading screen. Updates statistics, populates tables, updates charts, and populates filters.
  3. Filtering:
    • User changes a selection in any filter.
    • An Event Listener triggers applyFilters().
    • applyFilters() reads the filter values. Applies filterFinding to the existing data in allFindings to create filtered lists. Empties and repopulates the HTML tables with the filtered data. The charts and statistics remain unchanged (displaying the total).
  4. Viewing Details:
    • User clicks on the "Details" button.
    • An Event Listener triggers showFindingDetails() with the severity level and original index.
    • showFindingDetails() finds the full finding from the allFindings variable, populates the Modal's HTML, and displays it.
  5. Export:
    • User selects an export option.
    • An Event Listener triggers the appropriate logic (export all/filtered/by severity).
    • The appropriate logic prepares a list of findings (all findings, filtered findings by re-applying filterFinding, or findings only from the high/medium/low list).
    • The list is converted to CSV format by convertToCSV.
    • The file is downloaded to the browser by downloadCSV.
  6. Logout:
    • User clicks on the "Logout" button.
    • An Event Listener triggers logout().
    • logout() deletes the authentication state from sessionStorage and redirects to /login.html.

8. Further Considerations / Possible Improvements

  • Security: The current login is Client-side only and is not secure (easy to bypass). A server-side user authentication mechanism should be implemented (e.g., using Session Management or JWT) and the /api/findings Endpoint should be protected.
  • Data Storage: To avoid complete dependency on the SecurityScorecard API in real-time or to allow viewing historical data, MongoDB (or another database) can be used to store the findings fetched from the API. The server could then serve data from the DB instead of or in addition to live fetching.
  • Handling Pagination/Data Load: If the volume of findings is very large, performance issues may arise on the client-side (loading all data into browser memory). Pagination (dividing into pages) or Infinite Scroll can be implemented both in the Backend API (if SecurityScorecard API supports it) and in the Frontend.
  • Error Handling: Improve the display of error messages to the user in case of a failure in the SecurityScorecard API or the Backend.
  • API Call Optimization: The current data fetching method makes many API calls (Portfolios -> Companies * per company -> Factors). If the SecurityScorecard API allows for a more efficient way to fetch all relevant findings with fewer calls, this would improve performance and loading time.
  • Additional UI/UX: Table search, column sorting, more complex filtering options.
